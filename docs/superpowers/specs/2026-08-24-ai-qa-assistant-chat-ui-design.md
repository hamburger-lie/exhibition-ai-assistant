# AI 问答助手 Chat UI 设计规格

**版本：** V1.0  
**日期：** 2026-08-24  
**范围：** 仅 A 方 H5 Chat UI，以及由 Chat 进入的实体详情与展位地图界面  
**依据：** 已确认的 Chat UI 讨论、《API 接口契约与数据 Schema V1.0》及《H5 与知识库系统需求及分工说明书 V1.0》

## 1. 设计目标

- 首要服务到场观众，核心任务依次为找展商/产品、找展位、查活动和普通咨询。
- 以“专业展会服务助手”为主体，融入少量美业精致感。
- 保留主办方官方 Logo 和主色，其余 Chat 视觉重新建立轻量界面体系。
- 默认信息密度为“结论 + 必要说明 + 相关业务卡片”。
- 不采用紫粉 AI 渐变、发光球、机器人头像或夸张科技动效。
- 所有业务字段、引用、操作和地图定位只消费接口真实数据，不从 AI 文本猜测或补造。

## 2. 范围边界

### 2.1 A 方实现

- 空对话首屏、消息列表、输入区和流式状态展示。
- 展商、产品、活动卡片，引用、推荐追问和反馈。
- 实体详情页及展位地图高亮页。
- 停止生成、非流式降级、断流、超时、限流、无结果和恢复提示。
- 微信 WebView、iOS Safari 和 Android Chrome 的移动端适配。

### 2.2 不实现

- 真实知识库、搜索、RAG、Agent、数据导入和 B 方运营后台。
- 实时室内定位、路径规划、UWB/蓝牙导航。
- 接口未提供的报名、收藏、行程、断点续写或地图导航功能。
- V1 深色主题。

## 3. 信息架构

空对话状态本身作为首页，不额外增加“首页 → Chat”页面层级。用户点击快捷入口后，欢迎区收起并进入对话。

### 3.1 首屏结构

1. 轻量顶部栏：官方 Logo、“AI 问答助手”和“新对话”。微信容器已展示标题时隐藏重复标题栏。
2. 欢迎区：
   - 主文案：`你好，我是 AI 问答助手`
   - 辅助文案：`可以帮你查找展商、产品、展位和现场活动`
3. 四个 2×2 快捷入口：找展商、找产品、找展位、查活动。
4. 两条动态问题示例，使用文字链接，不叠加卡片层级。
5. 固定底部输入区，位于设备安全区上方。

### 3.2 对话结构

- 用户消息位于右侧，使用浅品牌色气泡。
- AI 回答位于左侧，以自然文本排版呈现，不套大气泡。
- 回答内容顺序固定为：正文 → 业务卡片 → 引用 → 推荐追问 → 反馈。
- 大欢迎区与快捷入口在第一条问题发送后收起。

## 4. AI 回答规范

### 4.1 正文

- 第一段直接给结论，后续使用最多 3–5 个短段落或列表补充。
- 展位号、馆号、日期和时间等关键数据可加粗，不使用大面积彩色高亮。
- 流式正文稳定增长，不显示跳动光标或装饰性逐字特效。

### 4.2 业务卡片

- 卡片纵向排列，不使用容易漏看的横向轮播。
- 同类结果优先展示 1–3 张；若接口返回更多，可在客户端折叠已加载内容，不新增接口。
- 缺失字段直接隐藏，不显示虚构占位值。

**展商卡：** 展商名称、主营品类、展馆/展位号、简短介绍，以及接口提供的“展位定位”和“查看详情”。

**产品卡：** 产品图片、产品名称、所属品牌/展商、分类、所在展位；仅在具备展位动作数据时显示“去展位”。

**活动卡：** 活动名称、日期、开始时间、场地和活动类型；只展示接口实际提供的详情或位置操作。

### 4.3 引用

- 默认折叠为 `参考依据 N`。
- 展开后显示真实 `source_id`、来源名称及 `page_or_row`。
- 正文可用 `[1]`、`[2]` 与来源对应，不把长引用直接塞入正文。

### 4.4 推荐追问与反馈

- 推荐追问最多 3–4 条，允许自动换行；点击后发送原始建议文本。
- 回答完成后才展示“有帮助 / 没帮助”。
- 负反馈通过底部选择层展示接口约定的原因与补充说明。
- 反馈与 `request_id/message_id` 绑定，失败不阻塞继续聊天。

## 5. 输入与流式交互

### 5.1 输入区

- 空内容时发送按钮禁用。
- 最大 1000 字，超过 800 字显示字数提示。
- 输入框默认一行、最多扩展到四行，超出后内部滚动。
- 发送后立即显示用户问题并清空输入框。
- 生成期间允许编辑下一条内容，但不允许重复发送。
- 发送按钮在生成期间变为明确的方形停止图标。

### 5.2 状态映射

界面把内部状态映射为用户可理解的文案：

1. `understanding` → 正在理解你的问题
2. `searching` → 正在查找相关信息
3. `reranking` → 正在筛选结果
4. `answering` → 正在整理回答

收到 `message.delta` 后状态行收起并展示正文。业务卡片、引用和推荐追问进入各自固定区域。

### 5.3 滚动与无障碍播报

- 用户处于底部附近时自动跟随输出；用户主动上滑后停止强制跟随。
- 离开底部时显示“回到最新”。
- 屏幕阅读器不逐字播报 token，只播报状态变化、错误和回答完成。

### 5.4 主动停止

- 使用 AbortController 终止请求，保留已生成正文与卡片。
- 回答尾部标记 `已停止生成`，输入区立即恢复。
- 不提供接口不存在的断点续写；用户可重新发送问题。

## 6. 异常与降级

| 场景       | 用户文案                   | 恢复操作               |
| ---------- | -------------------------- | ---------------------- |
| 网络不可用 | 网络连接异常，请检查后重试 | 重试                   |
| 请求超时   | 等待时间较长，请重试       | 重试                   |
| 429        | 当前咨询较多，请稍后重试   | 按 Retry-After 恢复    |
| 上游不可用 | 服务暂时不可用，请稍后重试 | 重试                   |
| 流式中断   | 回答中断                   | 保留已有内容并重新获取 |
| 会话失效   | 会话已恢复，请重新发送     | 重建匿名会话           |
| 无可靠结果 | 暂未查到可靠结果           | 提示修改关键词         |

- 收到 `message.error` 后立即终止本次流，不再等待 `message.done`。
- 流式不可用时调用现有非流式接口，保持同一消息 UI，仅显示“正在整理回答”。
- 错误必须包含恢复路径，不能只显示“请求失败”。

## 7. 详情页与地图

### 7.1 实体详情

- 展商、产品或活动卡片通过结构化 ID 打开对应详情页。
- 顶部仅保留返回按钮、实体类型和名称。
- 返回 Chat 后恢复消息、输入草稿和滚动位置。
- Chat 流在 SPA 全局状态中继续；返回后显示最新结果。

### 7.2 展位地图

- 地图页为全屏二级页面，包含返回按钮、展馆/展位号、可缩放地图和底部实体信息卡。
- 仅消费 `entity.card.actions[].type=highlight_booth`、`booth_id` 和 `map_shape_id`。
- 目标展位使用品牌色描边、标记和文字说明，呼吸效果必须轻微且支持减少动态效果。
- 缺少 `map_shape_id` 时展示文字位置与无法高亮的明确提示。
- 地图素材失败时保留馆号/展位号并提供重新加载。
- 不新增 `map.highlight` SSE 事件或导航能力。

## 8. 视觉系统

### 8.1 颜色

- 页面使用浅中性灰背景，卡片和输入区使用白色。
- 正文为深灰黑，辅助信息为满足对比度要求的中灰。
- 正式品牌主色从官方 Logo/品牌规范提取，不在开发阶段猜测色值。
- 品牌色用于发送、用户气泡、链接、定位和焦点状态；用户气泡使用品牌色浅色版本。
- 错误、成功和提示使用独立语义色。
- 普通文本对比度不低于 4.5:1，大型文本和 UI 图形不低于 3:1。

### 8.2 字体

- 字体栈：`PingFang SC`, `Microsoft YaHei`, `Noto Sans SC`, system-ui, sans-serif。
- 页面标题 18px/600；AI 正文 16px/400、行高约 1.65；卡片标题 16px/600；标签和按钮 14px/500；辅助信息 13px。
- 不使用小于 12px 的正文，不额外加载影响微信 H5 首屏性能的装饰字体。

### 8.3 间距、形状与层级

- 页面左右边距 16px，采用 4/8px 间距体系，主要使用 8/12/16/24px。
- 业务卡片圆角 12px，用户气泡圆角 16px，输入框圆角 20px。
- 卡片使用浅边框，阴影只用于浮层和固定输入区。
- 固定元素为内容预留安全区，不能遮挡最后一条消息。

### 8.4 图标与动效

- 使用同一套 SVG 线性图标，不使用 Emoji 作为结构性图标。
- 图标视觉尺寸以 20/24px 为主，点击区域不小于 44×44px，目标间距不小于 8px。
- 微交互 150–250ms，仅使用颜色、透明度或轻微 transform。
- 支持 `prefers-reduced-motion`，关闭动效后不影响操作与理解。

## 9. 响应式与兼容

- 移动优先，最低基准宽度 375px；不得出现横向页面滚动。
- 使用动态视口高度并处理顶部/底部安全区。
- 键盘弹起后输入区贴合键盘，消息列表仍可滚动。
- 验证微信内置浏览器、iOS Safari、Android Chrome，以及横屏可读性。

## 10. 接口事件到 UI 的映射

| SSE 事件          | UI 行为                        |
| ----------------- | ------------------------------ |
| `message.start`   | 创建 AI 消息占位并进入生成状态 |
| `status.update`   | 更新可理解的单行状态文案       |
| `message.delta`   | 从 `data.delta` 追加正文       |
| `entity.card`     | 依据结构化类型渲染业务卡片     |
| `citation`        | 加入折叠引用列表               |
| `suggestion.list` | 渲染最多 3–4 条推荐追问        |
| `message.done`    | 完成消息并展示反馈             |
| `message.error`   | 结束消息并展示对应恢复操作     |
| 未知事件          | 安全忽略并记录，不影响页面     |

## 11. 验收清单

- [ ] 空对话首屏、快捷入口和首条消息转场清晰。
- [ ] 正常回答、停止生成、非流式降级和流中断状态可验证。
- [ ] 展商、产品、活动卡片只读取结构化字段和动作。
- [ ] 引用只显示真实来源字段，缺失时不补造。
- [ ] 地图只使用 `highlight_booth`、`booth_id`、`map_shape_id`。
- [ ] 用户上滑阅读时不被流式输出强制拉回底部。
- [ ] 所有触控目标至少 44×44px，键盘和安全区不遮挡内容。
- [ ] 正文对比度满足 WCAG AA，状态不只依赖颜色。
- [ ] 375px 和横屏下无横向滚动或内容截断。
- [ ] 未实现任何 B 方知识库、检索、RAG、Agent 或运营后台能力。

## 12. 自检结论

- 设计覆盖了首屏、对话、卡片、引用、建议、反馈、异常、详情和地图的完整闭环。
- 所有关键交互均可映射到当前 V1.0 契约或 A 方既定 BFF/H5 能力。
- 未新增付款、报名、收藏、行程、路线规划或其他未约定业务。
- 开发执行以 `docs/superpowers/plans/2026-08-24-ai-qa-assistant-a-side-implementation.md` 为唯一实施计划，并以本规格作为 Task 7–10 的 UI 细化约束。
